## Dependencies and Execution Order

- Phase 1 establishes authorization and baseline and blocks every mutation.
- Phase 2 establishes the version contract and blocks generated adapter implementation.
- User Story 1 produces the immutable upstream candidate and CI artifact required by User Story 2.
- User Story 2 imports the exact candidate and produces the Android consumer implementation required by User Story 3 and User Story 4.
- User Story 3 can add its failing assertions in parallel with Android tests after import, but final desktop proof depends on the adopted shell.
- User Story 4 depends on all implementation and host checks. The upstream evidence update follows the downstream candidate commit.
- Merge order is upstream first, downstream second. Neither merge is performed without the user's final ritual.

## Parallel Opportunities

- T004, T005, and T006 affect separate test surfaces and can be prepared independently before T007.
- T015 and T016 cover browser/unit and Android instrumentation surfaces and can be authored independently after the kit import contract is known.
- T019 can begin after the adopted DOM contract is fixed while Android CI wiring proceeds.
- T021 can assemble static handover fields while host jobs run, but cannot claim final results early.

## Implementation Strategy

The MVP is User Story 1: a verified generated kit with a consumer-usable full-bleed AppFrame and dependency-free environment entry. The end-to-end slice is not complete until Glitchpad actually imports it and both actual-host classes pass. Implement test-first, keep repository commits distinct, and update evidence only from observed results.

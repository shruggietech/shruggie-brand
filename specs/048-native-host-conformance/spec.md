# Feature Specification: Native Host Icon and State Conformance

**Feature Branch**: `codex/048-native-host-conformance`

**Created**: 2026-09-23

**Status**: Implemented, pending PR review and CI

**Input**: Deliver the BrandBuilder-owned remedies for native rendering and role defects reported in #254, #255, #256, and #257, verify actual consumer resource selection where available, and prepare source and kits for owner review without publishing a release tag.

**Issues**: [#254](https://github.com/shruggietech/shruggie-brand/issues/254), [#255](https://github.com/shruggietech/shruggie-brand/issues/255), [#256](https://github.com/shruggietech/shruggie-brand/issues/256), [#257](https://github.com/shruggietech/shruggie-brand/issues/257)

## User Scenarios & Testing

### User Story 1 - Read native status and controls (Priority: P1)

As an ESO Weave operator, I can read an unavailable-capture status and distinguish disabled controls in either theme.

**Independent Test**: Inspect the consumer's actual status widget and a generated adapter exemplar in enabled, disabled, hover, focus, and theme states, measuring the rendered foreground and background pairs.

**Acceptance Scenarios**:

1. **Given** the Encounter History diagnostic path has been traced, **when** the generated native status guidance and exemplar are evaluated in dark theme, **then** their heading and message meet 4.5:1 text contrast and the ESO call-site correction is explicitly handed off.
2. **Given** a genuinely disabled control, **when** either theme is selected, **then** it remains visibly disabled while its label meets the project's 4.5:1 readability rule.
3. **Given** an enabled control, **when** it is hovered or focused, **then** text and meaningful state cues meet their applicable WCAG 2.1 AA thresholds.

---

### User Story 2 - Recognize applications on native hosts (Priority: P1)

As a Windows or Android user, I see a legible, intentional brand icon without an accidental dark square or doubled frame at common launcher and taskbar sizes.

**Independent Test**: Trace the exact resource selected by the ESO Weave executable and Glitchpad APK, then inspect generated and packaged pixels after representative native masks and light/dark composites.

**Acceptance Scenarios**:

1. **Given** the ESO Weave Win32 executable, **when** its icon appears on light or dark taskbars, **then** the mark has no unintended opaque square outside its approved visible silhouette and remains recognizable at 16, 24, 32, and 48 pixels.
2. **Given** the Glitchpad APK, **when** its adaptive icon appears under circular, rounded-square, or squircle masks, **then** the background covers the mask and no contrasting second frame or dark wedge obscures the mark.
3. **Given** separate taskbar, tile, adaptive, legacy, and listing roles, **when** a kit is used, **then** its integration guide names the correct asset and required host resource declaration for each role.

---

### User Story 3 - Trust role qualification across kits (Priority: P1)

As an integrator, I can select an asset for web/PWA, Android, iOS/iPadOS, macOS, Win32, or MSIX and know its declared role was checked for size, mask, theme, and alpha behavior.

**Independent Test**: Audit the generated role inventory and conformance matrix, generate all production kits, and run measured structural and visual checks on representative host compositions.

**Acceptance Scenarios**:

1. **Given** an installable web app, **when** its manifest is read, **then** ordinary and maskable purposes point to independently qualified assets.
2. **Given** any generated native role, **when** verification runs, **then** it checks the role's appropriate background, alpha, safe region, small-size, and host-mask behavior rather than applying one universal rule.
3. **Given** a package whose declared resource differs from the generated asset, **when** conformance is reported, **then** package selection remains an explicit consumer-adoption finding rather than a false generator pass.

### Edge Cases

- A label that looks disabled may actually be status text; semantic state determines which WCAG rule applies.
- System dark/light themes may select different resources or composite the same transparent resource against different surfaces.
- An adaptive foreground may be transparent while its background must fill the mask; Play artwork and Apple icons have different opacity rules.
- A mark with an approved enclosure must not be redrawn or stretched to remove a host frame.
- A package may pin an older kit. New generated bytes alone do not change the installed application.
- Optional raster capability may be absent; skips must be explicit rather than counted as passes.

## Requirements

### Functional Requirements

- **FR-001**: The work MUST record the exact ESO status widget, enabled state, theme source, effective text and background colors, and the relevant pinned kit and adapter.
- **FR-002**: The status heading and any meaningful enabled text MUST meet WCAG 2.1 AA text contrast on the rendered surface; meaningful control/state cues MUST meet applicable non-text contrast. Inactive-control text, though normatively exempt, MUST meet an additional 4.5:1 project readability rule.
- **FR-003**: The generated native style and its implementation guidance MUST define readable status, enabled, disabled, hover, focus, and light/dark states with repeatable native-state checks.
- **FR-004**: The work MUST trace ESO Weave's embedded Windows icon and Glitchpad's APK icon declarations and selected source assets, distinguishing generator output from consumer-pinned bytes.
- **FR-005**: Win32 taskbar and MSIX target-size/unplated assets MUST use an explicit transparent or intentionally plated policy. Tile and Store assets MUST retain their distinct role policy.
- **FR-006**: Android adaptive foreground, background, monochrome, legacy launcher, optional round icon, and Play listing roles MUST have explicit composition and integration rules. A background MUST cover every mask, and a visible second plate or wedge MUST not be introduced by the generator.
- **FR-007**: Web ordinary and maskable manifest roles MUST have separate qualified asset declarations, including suitable safe-region and background behavior.
- **FR-008**: A source-linked matrix MUST identify each generated icon role across PWA, Android, iOS/iPadOS, macOS, Win32, and MSIX, its alpha/background policy, safe content, masks, themes, sizes, host surface, and platform guidance.
- **FR-009**: Verification MUST inspect representative composited masks, boundaries, alpha, safe regions, and small-size appearance, including negative fixtures for accidental plates and uncovered backgrounds; role-specific rules MUST not reject valid transparency or valid opacity in other roles.
- **FR-010**: All changes MUST be in authoritative source, generator, guidance, and tests. Approved logo path geometry MUST remain byte-for-byte unchanged. Generated output MUST not be committed.
- **FR-011**: Every production kit MUST report zero verifier problems and zero glyph failures, and the full documented CI-equivalent validation MUST pass before merge review.
- **FR-012**: Findings that require an application to repin or package new kit bytes MUST be recorded as downstream adoption work, not represented as complete by this repository alone.

### Key Entities

- **Native role**: Platform, host surface, resource path, declaration, sizes, theme, mask, alpha and background policy, and source guidance.
- **Rendered state**: Semantic status, control state, theme, foreground/background pair, and measured contrast.
- **Consumer selection**: Application package or executable, selected resource, pinned source hash, and generated-kit counterpart.

## Success Criteria

### Measurable Outcomes

- **SC-001**: The generated native status exemplar and representative enabled/disabled controls each meet 4.5:1 text readability in both supported themes; enabled state cues meet 3:1 where applicable, and the ESO consumer call-site is identified for separate correction.
- **SC-002**: ESO Win32 icon frames at 16, 24, 32, and 48 pixels and Glitchpad icons under three masks have zero unintended background boundary or uncovered-mask failures in measured composites.
- **SC-003**: The role matrix accounts for 100% of generated platform icon roles and distinguishes ordinary versus maskable PWA assets.
- **SC-004**: The exact ESO executable and Glitchpad APK resource paths and pinned hashes are documented, with downstream repin work explicitly identified where necessary.
- **SC-005**: All production kits pass the full verifier and glyph gates with zero failures, and no approved source logo path bytes change.

## Assumptions

- This slice owns BrandBuilder source, output contract, tests, and integration guidance. It may inspect but does not edit ESO Weave or Glitchpad repositories. Their repins require separate consumer work.
- A role-specific change to icon composition may reuse already approved brand colors without altering logo geometry; any new identity color or changed path requires owner approval and is outside this slice.
- BrandBuilder 2.0.2 remains an unpublished candidate. S048 does not tag or publish a release, and the owner retains merge authority.

## Decision Log

### 2026-09-23 - Separate generated behavior from consumer adoption

ESO Weave's `Capture Unavailable` is consumer-local `ui.strong(...)`, which takes egui's active widget text color despite status semantics. BrandBuilder will improve its generated style and guidance and checks, but cannot repair the installed consumer without an ESO code change. Windows `build.rs` embeds a generated Win32 ICO and Glitchpad's APK contains copied kit resources, so those paths permit exact package attribution. Leave consumer-specific issues open until their repins and field checks are proven.

### 2026-09-23 - Use distinct role policies

PWA `any` and `maskable` must not share one unqualified image. Android adaptive background must fill the mask while foreground stays within the safe zone; Play listing remains a full square. Windows Win32 and MSIX taskbar assets need transparent outside-mark pixels where no approved plate exists, while tile and store may retain plates. Apple flat catalogs remain supported and are qualified separately.

### 2026-09-23 - Candidate identity is not a release

S047's 2.0.2 candidate was merged but not tagged. S048 changes compiler output and therefore must avoid publishing different bytes under the already recorded 2.0.2 package identity. Prepare a distinct candidate version, retain a dated migration impact, and await separate authorization to tag.

### 2026-09-23 - Preserve approved identity proof boundaries

Glitchpad's existing approved `square_enclosure.frame_role` already selects sulfur for the frame, so the mask background is derived from that role rather than adding a new source color field that would invalidate its continuity snapshot. ESO's Gate 1 derivative approval also rejects a new taskbar source field. Therefore Windows taskbar assets default to transparent for marks without an approved square enclosure, while explicit approved settings can override that general policy; logo paths and brand approval bindings remain unchanged. The I Heart PR Tours canonical proof renderer formerly hashed the entire `iconkit.py` module, including unrelated host-suite emitters. Preserve its approved settings fingerprint only while the exact four functions used by proof rendering and top-level module setup retain their original AST, and continue comparing every produced proof image; any change to a proof-used function still fails the approval gate.

No constitutional exception is planned. Role-specific checks fit the existing verifier and one source-linked matrix; a new preview subsystem is not justified.
